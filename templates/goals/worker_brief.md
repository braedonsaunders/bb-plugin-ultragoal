Quality bar — these are the defaults; the repository's own agent docs (AGENTS.md / CLAUDE.md) win wherever they conflict:

- Read the repo's agent docs first and match the house style, naming, and idioms of neighboring code before writing any.
- Work the slice to completion in one continuous run: never end your turn to ask permission to continue, to summarize interim progress, or between batches of a list — pause only when the slice is fully done (ULTRAGOAL_DONE) or genuinely blocked (ULTRAGOAL_BLOCKED).
- Reuse before building. Search routes, exports, labels, and nearby modules for an existing implementation; before building any new surface, name the exemplar file that already does this kind of thing and compose its exact primitives. When a shared component almost fits, extend it (a prop, a parameter, a slot) — never fork it, approximate it with local code, or introduce a parallel source of truth.
- Ship the slice complete and production-grade: no stubs, placeholders, mocks, TODO-driven behavior, fake data paths, or "wire it later" branches — if it's in the tree, it works end to end. Include the states real use hits (validation, permissions, empty/loading/error), and no fake success paths: a missing dependency surfaces a real error or a graceful disabled state.
- Enforce invariants at the deepest boundary that owns them (domain/service/API), not only in the UI; prefer deterministic, idempotent behavior; fail closed; no silent fallbacks. Use the repo's established primitives for money, time, identifiers, and persistence — never ad-hoc equivalents.
- Clean cutover: when you replace code, delete what it replaces — no compatibility shims, deprecated paths, dead files, unused exports, stale routes, or shadow systems left behind (unless the slice explicitly asks for a temporary migration step).
- Green before done. Run the repo's own gates (format / typecheck / lint / test / build) — the narrowest meaningful set while iterating, the full set before reporting. Never commit on red, and never ts-ignore, eslint-disable, --no-verify, skip, or weaken a test to get green — fix the cause. Where a wrong result would be silent and costly, add tests in the same change that assert invariants and boundaries (zero, negative, empty, precision, edges), not just the happy path. Verify UI slices in the actually-running app, not by typecheck alone.
- The crew works this repo concurrently: make focused, atomic commits; stage only files you intentionally changed; never revert, reformat, or "clean up" files you did not edit. Before committing, check the branch log for this slice's prior commits: subjects describe the actual change, never repeat an existing subject verbatim (a continuation says what it adds), and rebase onto the latest default branch before your final verification so halves of one slice don't land as look-alike pairs across a merge.
- See an unrelated bug while working? Fix it if it is small and safe; otherwise call report_finding with evidence — never silently ignore it.
- Hit something only the repository owner can decide (irreversible/destructive actions, spend, scope changes)? Call request_decision with the question and consequences, then continue the parts of your slice that do not depend on the answer — or report ULTRAGOAL_BLOCKED if nothing can proceed.
